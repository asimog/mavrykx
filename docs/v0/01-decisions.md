**Status:** current · **Date:** 2026-11-26
**This file owns:** every fixed, verified, recommended, assumed, open and risky item the design rests on. Nothing else in the set may contradict it.

## 1. How to read the labels

| Label | Meaning |
|---|---|
| **FD** | Fixed by the owner. Not reopened. |
| **VD** | Verified in a primary source. Evidence in the row. |
| **RD** | Recommended by this design. Binding once accepted; each row names its rejected alternatives and the condition under which a rejection may be revisited. |
| **AS** | Assumption. If wrong, the named recommendation changes. |
| **OQ** | Open question. A default is stated so work can continue. |
| **RK** | Risk. Each has a treatment and a falsifier. |

## 4. Recommended decisions

### Deployment and data

| ID | Recommendation | Why | Rejected | Change if |
|---|---|---|---|---|
| RD-1 | **Server-first; Electron is a client.** A solo lawyer runs the same server as a local service. | One code path for solo, LAN and remote | Desktop-only; client-side sync; SaaS | A measured solo install cannot reach "open and work" in 15 minutes |
| RD-2 | **One PostgreSQL database; `matter_id` on every legal row; RLS as defence in depth.** | One backup, one ACL, real isolation | Per-matter database; schema per matter; no RLS | A single matter exceeds the server's practical size |
| RD-3 | **Modular monolith with two process roles: `api` and `worker`.** | A small team can operate it; heavy work is isolated | Microservices; one process | A module needs independent scaling or a different runtime |
| RD-4 | **FastAPI + Pydantic Validation v2 + SQLAlchemy 2 async; the schema is one baseline SQL file.** Before pilot data, a schema change recreates the database; a numbered forward-only migration runner with an upgrade test and a **refusal test** exists **before any design-partner matter enters Postgres** - the pilot precedes any firm install. Downgrade is restore-from-backup, never in-place reversal | Pydantic-native, async, explicit SQL, no migration chain while the database is disposable | Django, Litestar, Flask, reversible in-place migrations | The first firm needs an in-place schema upgrade; then decide the mechanism |
| RD-5 | **DBOS is optional behind an `ExecutionEngine` interface.** A Postgres state machine and a `SKIP LOCKED` worker come first; DBOS is adopted if the recovery test fails. | No orchestration without demonstrated need | DBOS first; Temporal; Prefect; Celery | A crash-recovery test shows the simple model loses work |
| RD-6 | **Blobs on disk, content-addressed; metadata in Postgres; backup manifest.** | Large binaries in the database make backups painful | Bytea columns; S3-only | A firm mandates external object storage |
| RD-7 | **Postgres FTS + pgvector; no separate search or vector database.** | One store, one ACL, one backup | Elasticsearch, Qdrant, Pinecone, Redis | Retrieval p95 exceeds 400 ms at 2M chunks |

### The agent

| ID | Recommendation | Why | Rejected | Change if |
|---|---|---|---|---|
| RD-8 | **One agent config: system prompt + selected tool bundles + model policy.** | Capabilities scale; agents do not | Agent per function, court or jurisdiction | — |
| RD-9 | **A bundle is the unit of capability and evaluation:** tools + instructions + sub-agent tools + permissions + budget + evals + owner. | One place to add, test, version and retire a capability | A flat tool list; a folder of prompts | — |
| RD-10 | **Sub-agents are ephemeral tool implementations**: spawn, fork, map, verify, background; scope is the intersection with the parent; no commit/approve; depth ≤ 2; traced. | Parallelism without a second authority | Persistent specialist agents; peer agents | — |
| RD-11 | **The Pydantic AI Harness is the factory floor; Maverick is the legal control plane.** Compose Skills, SubAgents, Dynamic Workflow, Planning, Memory, Compaction, Step Persistence, Guardrails, Goal, budgets, approval mechanics, model routing and tracing. Add a legal capability pack for matter scope, legal skills, legal verification, human-only approval, audit, document tools, rule resolution and citation verification. **Do not** use `ApprovalReviewer` for legal actions, `Peers`, or `CapabilityCreation` in production. | The Harness provides the generic long-running agent machinery; reimplementing it is waste, and adopting it unconstrained is unsafe | Harness as execution only; a parallel home-grown harness; wholesale adoption | A Harness capability cannot be constrained by the legal gateway |
| RD-12 | **Every tool goes through a gateway** that checks scope, permission, policy, approval, idempotency, executes a service, records the event and validates the result. | One path from model to record | Direct service calls; direct SQL | — |
| RD-13 | **Context is a persisted package with a manifest.** | The run is reproducible and auditable | Transient prompt strings | — |
| RD-14 | **Human approval is a record bound to the subject hash.** A change makes it stale. | "Approve the draft" is meaningless if the draft changes | A boolean on the document | — |
| RD-50 | **The backend language is settled: Python + Pydantic.** The one-type-system law decides it: Pydantic models serve the API, the DTOs **and** the agent's tool contracts, because Pydantic AI consumes the same models. A TypeScript backend would put the application across a wire from the Python agent runtime — every tool call a cross-service hop with a second trust boundary, every contract duplicated in a second schema system. Effect TS's strengths (typed errors, fibre concurrency, managed resources) solve problems the modular monolith already solves; its OOXML ecosystem is thin where ours must be deepest. The UI keeps TypeScript with a generated OpenAPI client. | One runtime for app + agent; one contract source; the packaging budget stays Python-only | Effect TS or any TS backend with the agent as a separate Python service | The agent runtime itself became a first-class TypeScript library — it has not; FD-3 fixes Pydantic AI |
| RD-51 | **The runtime budget is fixed and counted.** A solo install is **three things**: the Electron shell (the editor engine is vendored content inside it), **one Python process** (solo runs `api` + `worker` in-process; the LAN splits the same codebase into two roles) and a **bundled PostgreSQL** — pinned binaries the installer starts, a service the app owns, not a prerequisite. x2t is a converter **binary invoked per conversion, never a daemon**. Everything else is excluded — no Node, no Redis or broker, no DBOS, no co-editing server. Any addition to the budget re-passes the 15-minute / 1.5 GB packaging gate **before it exists**. | The biggest technical risk is the runtime count; the answer is a hard budget, solo colocation, bundled Postgres, and the classification that separates vendored content and converter binaries from services | The worker as a mandatory separate service in solo mode; PostgreSQL as an external prerequisite; any uncounted runtime | The packaging spike fails and the deployment falls back to thin client + server appliance |
| RD-52 | **Process boundaries: containment by process, budget by runtime.** OCR and the document engine run as their own processes. Electron main keeps OS integration only; the workspace and the editor surface are separate renderer processes; **the agent's document engine is a managed Chromium-class builder process — the sole mutation engine** (proven in a hidden Electron window and headless Chromium; the desktop uses its shipped binary, the server uses the worker's portal-automation browser; without a browser binary it degrades to `ENGINE_UNAVAILABLE`): **`docx-core` is strictly read/verify** — anchors, diffs, checks, pinpoints; it never mutates a legal document. **x2t is a per-conversion subprocess**; **OCR is a per-job subprocess of the worker**, resource-limited. Processes are cheap and encouraged — crash containment, restart limits, timeouts; runtimes are the budget (RD-51) | One mutator halves the tracked-change/anchor/round-trip burden; verification stays deterministic and separate; the runtime risk is solved by separating *process* count (containment) from *runtime* count (the budget) | One monolithic process for editor + engine + OCR; a Node editor service; two active OOXML mutators; our own OOXML renderer (a Document IR — years of numbering/styles/tables fidelity work, the exact trap the vendor engine exists to avoid); any new runtime bought for containment | A contained process cannot meet its latency or recovery budget inside the counted runtimes |
| RD-53 | **Stateless execution, one authoritative record.** Two planes. The **record plane** is the firm server: PostgreSQL with RLS, the blob store, the api, and the **single `ToolGateway`** — the one place a tool call is scoped, permitted, executed against a service, audited and made idempotent. The **execution plane** is wherever the lawyer sits: the desktop runs the same Python code — agent loop, model call, the Chromium-class builder, x2t, OCR, portal browsers, optional local models — and holds **no local authority and no state to reconcile**. Every tool call crosses the live session to the one gateway; the files a run touches are a **disposable sha256 cache** fetched on demand (derived, never canonical); agent events append directly to the server with idempotency keys; approvals, commits and decisions are server transactions. **Access is standing, not per-run: a `matter_member` grant persists until revoked or a wall is raised; the live session plus that grant plus the bundle selection is the run's scope, re-checked by RLS on every call — so revocation is immediate.** Advocates on different matters share nothing but tool calls and append traffic. The AG-UI adapter runs on the node; the api hosts the relay that owns auth, client-tool filtering, the server-held history and `resume[]` validation against the stored history before anything forwards. Offline is out of scope (OQ-8); unappended traces on a lost desktop are lost working state, never a legal record | The common case (disjoint matters) has no contention and no server round-trip per agent turn beyond LAN milliseconds; the solo runtime already exists, so the node is zero new code paths; one gateway means "two doors, one corridor" holds by construction | Interactive runs queued through the server; signed portable run grants; local event ledgers with reconciliation; local version stores; CRDT documents | Offline work becomes a pilot requirement (then design the op-log rebase) |
| RD-54 | **A build order, never releases.** The whole system is one scope — no staged product versions, no MVP. 05 §3 encodes an **engineering sequence**: hard gates → the solo loop (one Delhi HC matter end-to-end) → firm + automation → remote/DR → triggered work. RK-1's falsifier is wired to the solo loop's completion: no breadth feature (shared rooms, portal automation, the relay) starts before a lawyer completes a real brief on the loop | Breadth outran software in the reference failure; sequencing is an engineering choice, not a product commitment | Product phases; version labels; MVP→v2→v3 framing | — |
| RD-55 | **Positions and registry facts are append-only records; status columns are derived summaries.** Fact positions (`fact_position`: party/advocate/court, basis, supersession) derive `fact.status` (court > advocate > party). Evidence status is three independent axes — authenticity, admissibility, inclusion — each an attributed event; a court finding is an event referencing the order id. An exhibit number is a **use of evidence in a proceeding** (`exhibit`), assigned by the advocate at marking — never a property of the evidence. Registry identity (registered/transferred/renumbered) is append-only `registry_event` rows: a transferred case is still the same proceeding | "A label is not a record" is our own first law; one status cannot hold "authentic but inadmissible, and included anyway"; one document can be Exhibit P-1 in the suit and R-3 in the appeal | Mutating status columns as the record; exhibit_no on evidence; a new proceeding row for a transfer | A position or axis value that cannot be represented as an attributed event |
| RD-56 | **Approval friction sits only on the irreversible boundaries.** `doc_apply` writes tracked, reversible changes — no per-call step-up; proposals get structured batch review in the inbox. `doc_commit`, filing-ready, send, grant and delete keep hash-bound step-up. **Never weaken a legal gate for speed.** Approval latency is a product health metric (RK-20) | Per-call step-up on reversible steps guarantees rubber-stamping and an unusable drafting loop; the legal gates stay hard | Step-up on every apply; weakening commit/filing gates to reduce friction | Batch review misses a wrong tracked change that is then committed — tighten apply; latency on the hard gates becomes a measured adoption blocker — redesign the gate, never remove it |
| RD-57 | **A scripted-model layer runs on every commit, bundle-scoped.** A deterministic scripted model drives the real loop through the real gateway — tool selection per bundle, cross-matter refusal, abstention on missing evidence, approval interrupt/resume, mid-run crash recovery — zero network, zero cost. Each bundle's eval suite carries its scripts; the bundle registry owns them; publishing a bundle runs them; the harness verification spikes (05 §2.8) are their permanent fixtures | The highest-leverage testing mechanism available: the loop's safety behaviours proven continuously, not once at spike time | Relying on offline evals and nightly runs alone for loop regressions | A loop regression ships because the scripted layer was skipped or allowed to go stale |
| RD-58 | **Portal download guards.** The job carries its `matter_id` — never a mutable global pointer; DOM selectors come from reviewed code, never model output; the browser profile is per-matter; the fetched artifact archives its full response context alongside its hash. Portal submission is human-only (05 §4) | A download must never bind to "whichever matter is current"; a model must never steer a court portal's DOM | A global current-matter pointer; agent-supplied selectors on any portal path | A download lands in the wrong matter's folder |
| RD-59 | **Client sign-off is optional, never a hardcoded gate.** A send-to-client action exists (email a draft or advice for review, under the `external_send` approval subject); a client reply is recorded as a contact-attributed decision when it arrives. A playbook **may** include a send-to-client step, as data | The client is not a user; client approval is a real record when it happens, but the engine never demands it | A mandatory client-approval gate in the engine | A firm wants client sign-off as a standing playbook step (it is data, not code) |
| RD-60 | **Hearing preparation is a designed capability.** Skills + a playbook + document types (brief, chronology, list of dates, cross-examination question lists anchored to documents) — and one context rule: **final-argument preparation retrieves matter-record-first** (past hearings, orders, evidence) before external authorities | The hearing cycle is in the product brief; `work_kind='hearing_prep'` and one table row are not a capability | Loose notes standing in for hearing prep; generic retrieval for final arguments | A hearing worked without the prep records, or final-argument prep that never reads the matter's own record |
| RD-61 | **Derived extractions pin their source text and go stale on re-OCR.** Every extraction (facts, dates, citations proposed from document text) records the `document_text` hash it was built from; a re-run marks derived extractions stale into the review queue | A corrected OCR silently invalidates nothing built on the faulty text — the opposite of temporal honesty | Extractions with no source pin; re-OCR leaving stale facts looking current | A fact built on superseded text still shows as current |
| RD-62 | **A completion contract per document type.** Required sections and fields are declared per type and checked deterministically before approval — a new verification kind | Structure is checkable without a model; "complete" becomes provable, not a feeling | A vibe-based completeness judgement | A document approved with a required section missing |

| RD-21 | **Readiness is bound to the exact document hash.** A new version resets it. | The bytes filed must be the bytes checked | A status flag | — |
| RD-49 | **No co-editing in the current scope; the upgrade path is defined and closed.** Concurrent human edits are sequenced by the document control service (single-writer commit, anchors + expected text, `DOC_STALE_TARGET`); the Euro-Office document server — a real co-editing engine but a separate AGPL-3.0 Node service — would be a later addition: a co-edit session opens from a committed version and saves back through the same commit path via `document-server-integration`, never owning identity, approvals or readiness. Licence review is mandatory before any firm-wide distribution of AGPL components | The packaging budget forbids another runtime; the legal record must not depend on a second service's storage; with the single-writer commit two humans never silently overwrite each other | Running the co-editing server now; last-write-wins editing; the document server as a record authority | Two lawyers must edit one DOCX at once **and** the packaging gate has passed with room for the extra service **and** the AGPL licence review is complete |

### Work, people and access

| ID | Recommendation | Why | Rejected | Change if |
|---|---|---|---|---|
| RD-22 | **Matter ≠ proceeding.** | One engagement can have a suit, an appeal and an execution | One case number per matter | — |
| RD-23 | **Hearing ≠ order; fact ≠ evidence; task ≠ deadline; document ≠ version; authority ≠ citation.** | Different legal meanings and failure modes | One status field for each pair | — |
| RD-24 | **A conversation is bound to one matter and one user at creation; a cross-matter message is rejected before the model.** | Prevents context bleed by construction | A global chat that switches matter | — |
| RD-25 | **A gate blocks a transition until a human clears it against frozen evidence.** Kinds: matter open, document approve, filing ready, rule publish, access grant, deletion. | Turns a duty into an enforceable workflow | An advisory checklist | — |
| RD-26 | **Contacts are firm-wide; client and party are roles.** | Deduplication needs one people graph | Free-text party names | — |
| RD-27 | **RBAC for firm functions; ABAC for matters; explicit deny walls.** | Firm functions and matter confidentiality are different problems | RBAC only; ABAC only | — |
| RD-28 | **Cross-matter reuse is an explicit grant** with purpose, fields, expiry and approver; it is logged. | Matter relationships must not grant access | Similarity-based retrieval | — |
| RD-42 | **The people model stays simple.** One `skill` table and one `playbook` table — versions are rows, `key@version` pinned; contact identifiers are columns on `contact`; grants and walls are per user. Teams are out of scope until a firm's size demands them. | The firm is small and often one person; fewer tables to build, secure and explain | Separate identity/version tables; team-based grants | A firm larger than ~50 users cannot be administered without teams |
| RD-43 | **The folder is the arrangement, not the store.** Every matter gets a folder tree seeded from `document_type`; documents carry `folder_id`; the canonical bytes stay content-addressed; export and per-matter backup write the real tree. | The lawyer sees and exports files arranged per matter without a second copy of bytes | OS folders as the canonical store | A firm mandates a filesystem-shaped canonical store |
| RD-46 | **Shared matter conversations.** `conversation.visibility ('private','matter')`; every turn is an attributed `message` row (execution state, never a legal record); agent turns are attributed to run + launching user, and a run in a shared conversation holds **only the launching user's grants**; delivery by a matter-scoped SSE channel on the existing `api` process; presence is ephemeral | The firm works in one room; attributed live shared chat is the expected shape; chat stays out of the legal record | A workspace/project entity; a second conversation authority; a message broker; the union of participants' grants as agent scope | The LAN-only assumption fails under real multi-office latency |
| RD-47 | **A submission is a composition, not an entity:** `task` + `document_version` + `approval` (subject hash) + `annotation` + a notification. Acceptance moves status; it never overwrites — the next edit is a new version | The review inbox is the surface; approval binds the exact hash | A `submission` table; a parallel review lifecycle; last-write-wins acceptance | A real workflow needs submission semantics the approval/gate vocabulary cannot express |
| RD-48 | **Task discipline.** `task.visibility ('matter','private')`; `task_document` links that never widen document access; reminders via the notifications module; task lists as playbooks (data, not tables); single assignee; appointments belong to a matter, and **hearing dates are forum-given, never self-scheduled** — the calendar is a derived view | Task access ≠ document access; private tasks; attachment without permission change are real small-firm behaviour | Multi-assignee; estimates, billable defaults, time entries — refused wholesale | A firm larger than ~50 cannot be administered without shared assignment |

|---|---|---|---|---|
| RD-29 | **Legal audit ≠ execution trace.** Audit stores hashes, actors and decisions; trace stores prompts, tools and cost. | A court record is not a debug log | One log for both | — |

MCP is the interface for **external** integrations through the Harness's MCP capability — reviewed, allowlisted, untrusted until verified — with an optional read-only MCP facade for a firm's own tooling later | One typed path, one audit path, one transaction per tool call; the Harness already treats MCP as a Tier-3 surface; no per-call serialisation hop and no extra processes | Every internal tool as an MCP server: a wire boundary and a hop on every call; the gateway would police a protocol instead of typed calls | A second consumer of Maverick capabilities requires a standard protocol surface |

## 7. Risks

| ID | Risk | Likelihood | Impact | Treatment | Falsifier |
|---|---|---|---|---|---|
| RK-1 | Breadth outruns the loop; the product becomes a toolkit | High | High | One reference pack, one pilot, no module without a completed task | The pilot completes a real matter without an engineer |
| RK-2 | Solo install is too heavy | Medium | High | Packaging spike | Clean install > 15 min or > 1.5 GB |
| RK-3 | Euro-Office packaging/licence/fidelity blocks distribution | Medium | High | Narrow adapter; acceptance tests; professional licence review (AGPL-3.0 and the custom DesktopEditors licence are named, VD-16); the Document Builder sidecar is a proven fallback engine path for agent edits | A tracked-change DOCX fails Word/LibreOffice |
| RK-4 | The agent bypasses a service or a permission | Medium | Critical | Gateway, no DB credentials, RLS, negative tests, deny default | Any tool reaches a table without a service |
| RK-5 | Cross-matter leak through retrieval or embeddings | Low | Critical | `matter_id` everywhere, RLS, mandatory filter, manifest, red team | A retrieval returns another matter's chunk |
| RK-6 | A stale rule produces a wrong filing | Medium | High | Effective dates, verifier, `unconfirmed` on stale | A check passes on a rule past review |
| RK-7 | Execution recovery loses work | Medium | Medium | Postgres state + idempotency; DBOS if the test fails | A restart duplicates a side effect or loses a step |
| RK-8 | Model cost or latency makes it unusable | Medium | Medium | Budgets, cheap extraction, caching, local option | Cost per matter exceeds the pilot threshold |
| RK-9 | The remote service becomes a data-access path | Low | Critical | E2E encryption, app auth still required, no content at relay, pen test | The relay can observe plaintext or bypass login |
| RK-10 | A single person holds the domain knowledge | High | Medium | Rules and skills as reviewed data with sources | A rule cannot be explained without the owner |
| RK-11 | The first reference pack is mistaken for the product | Medium | Medium | Label it as data; a second pack must be addable without code | Adding a second forum or document type requires a code change |
| RK-12 | `unconfirmed` and `waived` are treated as pass | Medium | High | UI, gate and report distinguish them; a waiver names the failed check | A filing gate opens on an unconfirmed citation |
| RK-13 | Harness 0.x API churn breaks the legal pack | Medium | Medium | Pin the exact Harness + Pydantic AI pair; wrap capabilities; read release notes | A minor upgrade changes a capability's contract the pack depends on |
| RK-14 | `ApprovalReviewer` approves a legal action on a human's behalf | Low | Critical | Never register it for legal actions; the gateway requires a human approval row; test | A commit/filing/send succeeds without a human decision |
| RK-15 | The Harness's 100+ capabilities become a new complexity | Medium | Medium | Curate a small set; one agent config; a manifest lists the exact capabilities | A run's capability set cannot be explained from its manifest |
| RK-16 | AG-UI protocol or adapter churn breaks the dock | Medium | Medium | Pin `ag-ui-protocol >= 0.1.19`; custom events are versioned; event fixture test | A protocol upgrade changes an event the dock depends on with no deprecation path |
| RK-17 | Court rule sources rot: URLs move, PDFs change silently, portals restructure | Medium | High | Scheduled fetch, content-hash snapshots, `unconfirmed` past the review date; every resolved rule names its instrument, clause and date | A published rule without a resolvable snapshot |
| RK-18 | A shared matter conversation widens the audience of every turn, and an agent in the room inherits nothing it should not | Medium | High | `message` rows carry `matter_id` + RLS; visibility is a column on the conversation; agent runs bind to the **launching user's** grants; attribution on every turn; negative tests | A non-member reads a message row, or a run acquires a grant its launching user does not hold |
| RK-19 | Stateless execution caches a matter's files on the node and risks stale reads | Medium | Medium | The cache is derived and sha256-verified, fetched on demand; commits carry the base version hash — `DOC_STALE_BASE` on drift; the per-document lease arbitrates; cache-staleness tests run across two nodes | A commit silently overwrites a newer version, or a node edits a stale base without rejection |
| RK-20 | Approval fatigue: step-up demanded on reversible steps trains lawyers to approve in under two seconds without reading evidence | High | High | Approval friction sits only on irreversible boundaries (RD-56): commit, filing-ready, send, grant, delete; tracked proposals get batch review; approval latency is instrumented as a product health metric | Median approval latency on tracked proposals under a few seconds; more than half of decisions accepted without opening the evidence |

## 8. Falsifiers for the whole design

1. A real matter cannot be represented without a new top-level entity.
2. A document cannot be versioned without a second document authority.
3. A matter cannot be isolated without a per-matter database.
4. The single agent cannot complete a task without a separate specialist agent.
5. A deterministic check cannot replace a model check for citations or format.
6. A solo installation cannot be made operable.
7. A rule cannot be resolved by scope and date without a court-specific code branch.
8. A court rule cannot be fetched, verified and published as data by a non-engineer.
